# Redis Task Queue Contract

How `kalibra-api` (Spring Boot) and the Adaptive Engine exchange work through Redis
Streams. The engine side is implemented. It is controlled by `REDIS_ENABLED`: **on by
default in the Docker Compose stack** (which includes Redis) and off by default in a bare
run.

## Flow

```
kalibra-api ──XADD──▶ kalibra:engine:tasks ──XREADGROUP (group adaptive-engine)──▶ engine
kalibra-api ◀──XREADGROUP (its own group)── kalibra:engine:results ◀──XADD── engine
```

1. `kalibra-api` publishes one entry per task on `kalibra:engine:tasks`.
2. Every engine instance reads through the consumer group `adaptive-engine`, so each task
   is processed by exactly one instance at a time.
3. The engine runs the same use case as the REST endpoint of the same name, publishes the
   outcome on `kalibra:engine:results` and only then acknowledges (`XACK`) the task.
4. `kalibra-api` consumes the results stream with its own consumer group, matches each
   result by `taskId`, persists it and acknowledges it.

## Task entry (`kalibra:engine:tasks`)

Flat stream fields, all strings:

| Field | Required | Content |
|---|---|---|
| `taskId` | yes | UUID generated by `kalibra-api`; correlates the result |
| `type` | yes | `mastery-estimates`, `exercise-generations` or `curricular-extractions` |
| `payload` | yes | JSON object: exactly the body of the equivalent REST request |

| `type` | Payload = body of | Result = body of |
|---|---|---|
| `mastery-estimates` | `POST /api/v1/mastery-estimates` | its `201` response |
| `exercise-generations` | `POST /api/v1/exercise-generations` | its `201` response (a list) |
| `curricular-extractions` | `POST /api/v1/curricular-extractions` | its `201` response |

Example (`redis-cli`):

```
XADD kalibra:engine:tasks * taskId 3f0c…e1 type mastery-estimates
     payload '{"studentId":"…","subtopicId":"…","priorProbability":0.42,"outcome":"CORRECT"}'
```

## Result entry (`kalibra:engine:results`)

| Field | Always | Content |
|---|---|---|
| `taskId` | yes | Same value as the task (empty only if the task had none) |
| `type` | yes | Same value as the task |
| `status` | yes | `SUCCEEDED` or `FAILED` |
| `completedAt` | yes | ISO-8601 UTC timestamp |
| `result` | when `SUCCEEDED` | JSON: body of the REST response |
| `error` | when `FAILED` | JSON: RFC 9457 problem details (`type`, `title`, `status`, `detail`, `instance`) |

`error.status` follows the REST status codes, so `kalibra-api` handles both transports alike:

| `error.status` | Meaning | Suggested handling in `kalibra-api` |
|---|---|---|
| `422` | Invalid task or payload, invalid probability, or a material that is itself unusable | Do not retry; mark the material as "ingestion error" for `curricular-extractions` |
| `409` | Generation run asked for an extra attempt | Do not retry |
| `502` | An AI provider failed after the engine's own retries, is unreachable or is not configured | Retry later by publishing a new task |
| `500` | Unexpected error, or the task exceeded `REDIS_MAX_DELIVERIES` | Alert; retry manually |

For `curricular-extractions`, `422` is reserved for a material at fault: an unsupported
`format`, a document that Mistral OCR rejects (`400`, `413`, `415` or `422`) or a material
without extractable text. A missing or rejected `MISTRAL_API_KEY` (`401`, `403`), a
transport error or timeout, `408`, `429`, `5xx` and any other provider failure are `502`:
the material is fine and the task can be published again later.

## Delivery guarantees

- **At least once.** The task is acknowledged only after its result is published. If the
  engine dies mid-task, the entry stays pending and another instance reclaims it after
  `REDIS_CLAIM_IDLE_MILLISECONDS` (default 15 min). `kalibra-api` must therefore store
  results **idempotently by `taskId`**.
- **Long tasks keep their claim.** While a task runs, the engine refreshes its pending entry
  every third of the idle window, so slow generations are not reclaimed by mistake.
- **Poison tasks stop.** A task delivered more than `REDIS_MAX_DELIVERIES` times (default 3)
  is published as `FAILED` (`500`) and acknowledged instead of retried forever.
- **Bounded load.** Each process runs at most `REDIS_WORKER_CONCURRENCY` tasks at once.
- **Bounded memory.** The results stream is trimmed to about `REDIS_RESULTS_MAX_LENGTH`
  entries; `kalibra-api` should also trim the tasks stream it owns.

## Enabling it

1. `docker compose up` already runs Redis 8, points the engine at it and turns the worker
   on. For any other deployment set `REDIS_ENABLED=true` and `REDIS_URL` for the engine.
2. In `kalibra-api`, publish tasks with `XADD` and consume `kalibra:engine:results` with a
   consumer group (Spring Data Redis `StreamMessageListenerContainer`).
3. Check `GET /health/ready`: the `redis` component must be `UP`.

The gap-map cache in Redis belongs to `kalibra-api` only; the engine never touches it.
